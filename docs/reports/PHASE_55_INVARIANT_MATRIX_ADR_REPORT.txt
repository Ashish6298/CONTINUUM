3. ARCHITECTURAL DECISION (ADR-001) EVALUATION & SELECTION
--------------------------------------------------------------------------------
A. Sufficiency Evaluation of Existing Storage:
   - Existing Persistence: Single monolithic `.continuum/state.json` file written
     via atomic `.tmp -> replace()` swaps.
   - Sufficiency Finding: INSUFFICIENT for the v1.4.0 target scale (Requirement 27:
     thousands of activities, tens of thousands of checkpoints).
   - Rationale: Storing all activities and checkpoints inside a single JSON file
     requires O(N) memory allocation on every load/save, multi-megabyte disk writes
     for single checkpoint appends, and high risk of file-lock contention on Windows
     NTFS (`PermissionError`). Most critically, it violates Invariant I-17 (bounded
     memory retrieval).

B. Chosen Architecture: Hybrid Partitioned JSON + Embedded SQLite Derived Index
   1. Authoritative Store (Crash-Safe Partitioned JSON):
      - `.continuum/activities/<activity_id>/activity.json`
      - `.continuum/activities/<activity_id>/checkpoints/<checkpoint_id>.json`
      - Written with atomic `.tmp -> replace()` swaps.
      - Plain text, human-inspectable, Git-versionable, zero external dependencies.
   2. Derived Index Store (Embedded SQLite Database):
      - `.continuum/index.db` using Python standard library `sqlite3`.
      - Fast B-Tree indexes for timeline pagination, filtering, and FTS5 search.
      - Invariant I-06 Compliance: SQLite database is strictly a derived index.
        If deleted, corrupted, or desynchronized, it can be 100% deterministically
        rebuilt by scanning the authoritative JSON partitions.
   3. Dependency Policy: ZERO third-party dependencies (`dependencies = []`).

5. TRANSACTION & RECOVERY BOUNDARIES SPECIFICATION
--------------------------------------------------------------------------------
- COMMIT:
  * Mechanism: .tmp write -> fsync -> atomic replace().
  * Failure: Unlink .tmp; raise CommitFailedError; live records unmodified.
- BRANCH:
  * Mechanism: Atomic Activity creation pointing to parent checkpoint.
  * Failure: Discard branch initialization; origin activity untouched.
- RESTORE:
  * Mechanism: Pre-restore snapshot -> workspace update -> RESTORE checkpoint.
  * Failure: Rollback to pre-restore snapshot; raise UnsafeRestoreError.
- IMPORT:
  * Mechanism: In-memory schema and relation validation before any disk write.
  * Failure: Abort immediately on first error; raise ImportValidationError.
- RETENTION:
  * Mechanism: Ancestry graph walk protecting milestones and branch heads.
  * Failure: Abort pruning; raise RetentionLimitError.
- MIGRATION:
  * Mechanism: Staging directory migration -> atomic swap -> pre-migration backup.
  * Failure: Rollback to backup; raise MigrationError.

6. USER-SAFE ERROR HIERARCHY
--------------------------------------------------------------------------------
Base Class: `ContinuumUserError`
Subclasses:
- `InvariantViolationError`: Explains invariant constraint violations.
- `CommitFailedError`: Explains write/disk failures without leaking file paths.
- `UnsafeRestoreError`: Explains restore validation rejections.
- `ImportValidationError`: Details validation errors without mutating storage.
- `RetentionLimitError`: Explains why retention pruning cannot proceed safely.
- `MigrationError`: Provides actionable migration recovery steps.
